1. Overview

pyaces lets Python call the computational modules of the Fortran quantum-chemistry program ACES II (ACES_PROGRAM/aces2) directly. Classic ACES II builds one executable per module (xjoda, xvscf, xvcc, …); a driver runs them in turn and they exchange state through files on disk (JOBARC, MOINTS, …). pyaces links those modules into a single shared library, aces2py.cpython-312-x86_64-linux-gnu.so, and puts a Python wrapper generated by numpy's f2py on top.

Python: import aces2py; aces2py.Init(); aces2py.Runcc(0); aces2py.Dgetrecpy("TOTENERG", e)
▼ f2py C wrapper (Main/gen/aces2pymodule.c)
pyaces Fortran shims: Main/init.F, a2_pyf/run*.F, a2_pyf/*recpy.F, *lstpy.F, aux_pyaces/*.F
▼ static link (-Wl,--start-group … about 107 archives)
aces2 archives: aces2/lib/lib*.a (joda, vmol, vscf, vtran, intprc, vcc, lambda, vee, props, intgrt, dirmp2, …), some replaced by patched copies in build/patched_libs
▼
Intel MKL ILP64 (sequential) and the Intel Fortran runtime

1.1 Key facts

  • The aces2 sources are never touched. pyaces links aces2's .a files as they are. Only for archives with collisions does it make temporary copies and rename symbols in them with objcopy. The aces2 tree is shared with the classic driver and its test suite.
  • All integers are 64-bit. aces2 and pyaces are compiled with -i8, and MKL is linked in its ILP64 flavour.
  • One calculation per process. aces2's COMMON-block state assumes a single use; calling Vtran/Vcc twice in one process has been seen to converge silently to a wrong answer.
  • The main risk is at link time. Routines that share a name but differ in implementation were harmless when every executable was linked on its own. In one .so they collide, and the linker silently picks one. The safeguards for this are the core of chapters 5 and 6.
  • Tests reuse the aces2 fast suite. Of its 158 cases, the 60 that pyaces can run (SCF 9, CC 39, EOM 8, KS 3, PCCD 1) are executed and their JOBARC energies compared with the reference values to within 1×10-6 Eh.

1.2 How to read this manual

If you are new to pyaces, read chapter 2 (which files are live), then chapter 4 (the build), then chapters 7–8 (API and running). Before exposing a new Fortran routine or linking another aces2 module, read chapters 5, 6 and 10. Chapter 11 lists the defects still present in the code.

3.2 configure and the module set

The top-level ./configure finds a toolchain and writes build_config.sh. The top-level build.sh exports the ACES_PROGRAM_MODULES recorded there, and pyaces/build.sh reloads exactly that set after module purge (aces_load_modules in cmake/env.sh). PYACES_MODULES, which the CMake superbuild sets, takes precedence; if neither is set it falls back to the HiPerGator set (intel/2025.1.0 openmpi/5.0.7 python/3.12). PYACES_MODULES="" skips the module load and uses the current environment.

# ccsd server
./configure --modules="intel/oneapi_2023.2.0 python/3.12.3" --np=4
# local workstation: build_config.sh has ACES_PROGRAM_MODULES="intel-ompi/2024.0"
Caution: include a Python module in the set. If module purge unloads the Python that has numpy, the f2py step fails.

3.3 Locale

pyaces/build.sh forces export LC_ALL=C (line 19). The globs and sort calls in the script set archive-member order and -l order, and that order decides which copy of a duplicated routine gets linked. For the same reason the aces2 makefile wraps its source lists in $(sort …): GNU Make 4.2 does not sort wildcard results, and 4.3 sorts them by locale.

3.4 Build commands

./build.sh aces2 pyaces          # top level: aces2, then pyaces
./build.sh pyaces                # only pyaces, when aces2 is already built
bash pyaces/build.sh             # run directly (set PYACES_MODULES or ACES_PROGRAM_MODULES yourself)

The log is build_logs/unified_build_pyaces.log. On the shared local workstation, stay inside the allocated cores: taskset -c 20-23 flock -s /tmp/qtoy-bench.lock ./build.sh pyaces. On the ccsd server, build only through PBS (build_logs/build_ccsd.pbs).

After changing compiler flags: make does not track flag changes. After changing aces2 flags, remove its build output with git clean -fdXq aces2 and rebuild. pyaces wipes and recreates gen/ and build/ on every build.

4. Build pipeline (build.sh)

4.0 Setup (lines 1–36)

  • Pick the Fortran compiler: $PYACES_FC, else ifx, else ifort.
  • Choose the module set (PYACES_MODULES, else ACES_PROGRAM_MODULES, else the HiPerGator set) and load it with aces_load_modules from cmake/env.sh: module purge; module load, nothing for an empty set, a warning and the current environment on a host without a module command.
  • Exit if MKLROOT is empty. MKL=$MKLROOT/lib/intel64 (or $MKLROOT/lib).
  • export LC_ALL=C.
  • Ask the running python3 for NUMPY_INC, PY_INC and F2PY_SRC (numpy's f2py/src).
  • cd Main; rm -rf gen build; mkdir -p build.

4.1 Source lists

PYF_SOURCES lists the sources whose routines make up the Python interface. f2py scans them and wraps every routine it finds; there is no .pyf. Passing every source would also wrap internal helpers, whose all-caps F77 names trip over case mangling. Hence the hand-picked list.

SOURCES (lines 52–62) is every Fortran file to compile: a2_pyf/*.F except rungrads, run1props and run, plus Main/init.F, Main/aces2_main.F and aux_pyaces/*.F. So a2_get*/a2_put*, getlstpy_dbg, get1epy and returnpy are linked but not exposed to Python.

Fortran flags

FFLAGS="-diag-disable=10448 -i8 -fPIC -fp-model strict -O1 -assume minus0 -qopenmp \
        -D__fortran -D__fortran77 -D_INTEL -D_RECL_IS_WORDS_ \

  • -i8: 8-byte default INTEGER, matching aces2 and MKL ILP64.
  • -FI: fixed-form source. -D__fortran77 selects the F77 branch of aces2's headers.
  • Headers come from aces2's include and acescore/include. Main/init.F and Main/aces2_main.F include them the same way as every other pyaces source.

Link command

ifx -shared -nofor-main -o build/aces2py${EXT_SUFFIX} build/*.o \
    -L$PATCHED_LIBDIR $LIBDIRS -Wl,--start-group $LIBNAMES -Wl,--end-group \
    -L$MKL -Wl,--start-group -lmkl_intel_ilp64 -lmkl_lapack95_ilp64 \

  • LIBDIRS/LIBNAMES are regenerated every build from find $ACES -maxdepth 2 -iname "*.a" (sorted, de-duplicated). All aces2 archives sit in one group, so circular dependencies resolve.
  • -L$PATCHED_LIBDIR comes first, so a patched copy wins over the original archive of the same name.
  • -nofor-main stops ifx from requiring its own main program.

5. Linking into one .so: symbol collisions and their fixes

The classic ACES II build links each module into its own executable. Routines that share a name but not an implementation, such as vcc's FINISH and lambda's FINISH, were therefore harmless. pyaces puts all of them into one .so, so the linker picks one copy and hands it to every caller, without a warning. The result is a segfault, @GETLST: List (x,y) does not exist, or a silently wrong energy. The pyaces link step has four safeguards against this.

5.1 Localizing MAIN__

Twelve modules (hbar joda lambda pccd props vcc vee vmol vmol2ja vscf vtran intprc, MAIN_COLLISION_MODULES) contain a Fortran PROGRAM, so each defines MAIN__. The standalone executables need it, but in one .so it means "multiple definition of MAIN__". The build extracts each of these archives with ar x into a temporary directory, applies objcopy --localize-symbol=MAIN__ to the objects that define it, and repacks them as build/patched_libs/lib<mod>.a. aces2's own .a files are not modified.

5.2 tools/localize.txt: renaming the losing copy

Each rename <module> <symbol> line in tools/localize.txt (60 today, each with its reason) becomes a module:symbol pair in build.sh's EXTRA_LOCALIZE_SYMBOLS, and each extract <module> line an entry of EXTRA_LOCALIZE_MODULES. For each pair the build applies objcopy --redefine-sym sym=pyaces_<mod>_sym to every object in that module's archive. The definition and the module's own calls are renamed together, so the losing module keeps using its own implementation under the new name, and the original name is left to the winner.

Rule: a rename only takes effect if its module is extracted, i.e. in MAIN_COLLISION_MODULES or on an extract line. Before patching, the build checks every pair: if the module is not extracted, or its archive defines no T symbol of that name, the build stops with tools/localize.txt has renames that cannot be applied. Keep extract lines that have no rename of their own (libr2): repacking an archive reorders its members, which can change which duplicate wins.

The build used --localize-symbol at first, but that sent the losing module's own calls to the winner (lambda's vlamcc ended up calling vcc's FINISH), so on 2026-08-11 it switched to --redefine-sym.

5.3 NEWLY_LINKED_MODULES: bulk handling of re-enabled modules

a2mix aux rpa scrnc were .skip directories until they were re-enabled, so the classic build never linked them next to the other modules. The build collects the T symbols of every aces2/lib/lib*.a and automatically adds to EXTRA_LOCALIZE_SYMBOLS every symbol (except MAIN__) that one of these four modules shares with another module. The log shows shadowed by <mod>, renaming: ….

5.4 COMMON blocks that shadow subroutines

A Fortran COMMON /abcd/ emits a tentative symbol abcd_ (C in nm). A subroutine ABCD is also abcd_. If the COMMON satisfies the reference before the linker extracts the object holding the subroutine, call abcd jumps into zero-filled BSS. The symptom is a SIGSEGV on instruction fetch, recognisable in gdb by si_addr == $pc.

  • rename-definer: if only the defining module calls the routine, add rename <definer> <sym> to tools/localize.txt (e.g. rename intgrt abcd_).
  • rename-commons: if other modules call it too, renaming would orphan them, so the COMMON block has to move instead.

Nine latent cases (mopac deriv/grid/local/polar, nddo guess/local, aces2 and ccd_light energy, pdens one/tab, vdint sym2) were renamed ahead of time.

5.5 Keeping patched_libs clean

build/patched_libs comes before aces2/lib on the -L path, so a stale file there shadows the real archive. A libintgrt.a left over from an experiment once caused undefined symbol: intgrt_run_. The directory is now removed and rebuilt on every build.

5.6 Finding out which copy won

# First choice: ask the linker (add to the link command)
-Wl,-trace-symbol=getdt1_
# Fallback: match the size in the .so against the archives
nm -S Main/build/aces2py*.so | grep ' getdt1_$'
nm -S ../aces2/lib/libvcc.a ../aces2/lib/libvee.a | grep ' getdt1_$'
# COMMON shadow check: B or D instead of T means data, not code
nm Main/build/aces2py*.so | grep -E ' (abcd_|hbar_)$'
# Which symbol does a pyaces object actually call?
nm Main/build/runhbar.o | grep -i hbar

6. The link-resolution audit (collision_audit.py)

It runs automatically as build step 6 and can also be run by hand. It needs an already built Main/build/aces2py*.so.

python3 tools/collision_audit.py            # report against the baselines
python3 tools/collision_audit.py --update   # overwrite both baseline files with the current findings
python3 tools/collision_audit.py --calls    # fail if a pyaces call binds to data (run by build step 5)

6.1 What it checks

(1) Resolution differences. For every symbol defined by more than one module:

  1. Reconstruct the classic link order from ACES_LINK_LISTS in aces2/Makefiles/GNUmakefile.
  2. Identify the copy actually in the .so by its nm -S size (skipped if sizes cannot tell the copies apart).
  3. For each calling module, compare it with the copy the classic build would have given (its own copy, otherwise the first library in its link list that defines the symbol).
  4. If the two differ, and their comment-stripped sources differ too, report symbol winner classic caller.

Pairs already renamed by build.sh are excluded; the audit reads the rename lines of tools/localize.txt and NEWLY_LINKED_MODULES from build.sh.

(2) COMMON shadows. It reports symbols that are T in one archive and C in another and B/b/D/d in the .so, with a verdict of rename-definer or rename-commons.

(3) Calls bound to data (--calls). Every U symbol in pyaces's own Fortran objects (Main/build/*.o except the two C objects) is a call, because Fortran references COMMON blocks as C. If the .so defines that name as data (B/b/D/d), the call would jump into a COMMON block. This catches the case (2) cannot, where no subroutine of that name exists anywhere (the hbar_ defect). It is not advisory: build step 5 runs it and any hit fails the build.

6.2 Reading the output

@COLLISION_AUDIT: 0 subroutines shadowed by a same-named COMMON block ...
@COLLISION_AUDIT: 296 resolution differences (296 in the baseline)
  resolved since the baseline: ...             # in the baseline, now gone
@COLLISION_AUDIT: NEW resolution differences ...
    getdt1_   .so gives vcc, lcct expects lcct   # new: needs action

6.3 When NEW entries appear

  1. Compare the two implementations (argument count, list numbers, what they compute). If they compute the same thing, the entry can be accepted into the baseline.
  2. If they differ, choose the copy to rename and add rename <loser> <symbol> to tools/localize.txt, with an extract <loser> line if the module is not extracted yet.
  3. Rebuild pyaces and confirm the NEW entry is gone and no other symbol flipped. Adding a module to the processed set can change how its other symbols resolve.
  4. Update the baseline with --update only after the suite has passed.
The baseline is not a to-do list: its 296 entries are known, accepted differences. Renaming 42 "safe-looking" entries in one pass once dropped the suite from 45 to 31 PASS. Also, ACES_LINK_LISTS only covers modules that build executables, so callers inside library modules (libr, libr2, tools, acescore, …) are invisible to the audit. Calls from pyaces's own objects into COMMON blocks are covered separately by --calls.

7. The aces2py API

7.1 Signatures come from the Fortran sources

f2py builds the module from the sources in PYF_SOURCES alone. (Until 2026-10-23 a Main/aces2.pyf was passed as well; f2py then built the module twice and the source scan overwrote the .pyf version, so the .pyf never took effect. Dropping it left aces2pymodule.c byte-for-byte the same.) As a result:

  • Python names follow the capitalisation in the source: Init, Dgetrecpy, IGetrecpy (capital G).
  • Argument types and intents come from the source. To change an intent, put a Cf2py intent(...) line in the .F file. Every Run* takes an Iuhf argument.
  • No COMMON blocks (/flags/, /jobarc/, /lists/, …) are exposed; read state through JOBARC records instead.
  • Check exact signatures with print(aces2py.Runcc.__doc__) or the docstrings in gen/aces2pymodule.c.

7.2 Array arguments

Every function is a Fortran subroutine. Apart from the two functions in 7.4 that return a value, results are written into numpy arrays the caller passes in. f2py wraps those arrays as "input", so if the dtype or memory layout is wrong it silently passes a copy, and whatever Fortran writes is lost with the copy.

Always pre-allocate C-contiguous 1-D arrays: np.zeros(n, dtype=np.float64) for reals, np.zeros(n, dtype=np.int64) for integers. Record names are 8 characters, padded with blanks ("IFLAGS ").

7.3 Calculation drivers

Iuhf: 0 = RHF, 1 = UHF/ROHF (Integer*8 on the Fortran side, long long in C). No driver calls aces_fin, so the session stays open afterwards and records can be read.

A table of list numbers is in pyaces.moio (e.g. T2(Ij,Ab) = 46, T1(AI) = 901, W<AB||IJ> = 14). Use list_numbers(label), list_labels(number) or distribution_numbers(label); some labels and numbers repeat, so each returns a list. The entries were transcribed by hand and have not been checked one by one against the ACES II sources.

7.6 AO integrals

SignatureDescription
Get1ehpy(Name, Dest, Ndim)Read "overlap", "oneh" or "kinetic" from the IIII file and expand it into a full Ndim×Ndim matrix (Ndim = NBASTOT). Without symmetry the basis is the AO basis. With symmetry it is the SO basis with the functions in irrep order (NUMBASIR), and the matrix is block diagonal; the SCF eigenvectors SCFEVCA0 are in the same basis, so CTSC = 1.

7.7 The pyaces Python package

python/ holds a small package on top of aces2py. It does not replace the raw module (still available as pyaces.ext(), names unchanged); it adds lower-case functions, return values instead of output arrays, and a way to run a calculation without risking the caller's process.

# aces2py is found in pyaces/Main/build, or in $PYACES_EXT_DIR

8. Running calculations

8.1 Runtime environment

  • Working directory: must contain ZMAT and GENBAS. ACES writes JOBARC, JAINDX, IIII/IJIJ/IIJJ/IJKL, MOINTS, MOABCD, MOL, NEWMOS and others into the same directory. Memory size comes from the ZMAT keywords.
  • Libraries: the Intel runtime and MKL are needed. Load the same module set as for the build, or set LD_LIBRARY_PATH. Otherwise the import fails with libmkl_intel_ilp64.so.2: cannot open shared object file.
  • Import path: put pyaces/Main/build on sys.path or PYTHONPATH.

8.2 Basic usage

import os, sys, numpy as np
os.chdir("/path/to/workdir")                 # contains ZMAT and GENBAS
sys.path.insert(0, "/path/to/ACES_PROGRAM/pyaces/Main/build")
import aces2py

aces2py.Init()                               # skip for Runee
aces2py.Runcc(0)                             # 0 = RHF, 1 = UHF/ROHF

e = np.zeros(1, dtype=np.float64)
aces2py.Dgetrecpy("TOTENERG", e)
print("E =", e[0])
print("TOTENERG length:", aces2py.Getreclenpy("TOTENERG"))

8.3 Reading and modifying records

iflags = np.zeros(100, dtype=np.int64)
aces2py.IGetrecpy("IFLAGS  ", iflags)
iflags[1] = 1                                # IFLAGS(2) = CALC
aces2py.Iputrecpy("IFLAGS  ", iflags)
aces2py.Acesjafin()                          # flush before an external executable reads JOBARC
# ... run ../aces2/bin/xvtran etc. as subprocesses ...
aces2py.Acesjainit()

8.4 Rules

  • One calculation per process. Do not run several ZMATs in a row in one process. The test runner starts a new process for each case.
  • Do not run the same module twice. Calling Vtran/Vcc twice in one process has converged to wrong values. This includes calling Runhbar after Runcc.
  • Runee calls Joda itself. Do not call Init() before Runee. Every other entry point, Runpccd included, needs Init() first.
  • Out of scope: geometry optimisation, frequencies, analytic derivatives (gradients and Hessians), Brueckner, HFSTABILITY=FOLLOW and CCSD(TQ) cannot run under pyaces yet (rungrads.F is excluded from the build).

8.5 FNO special case (pyaces_run_case.py)

When ZMAT contains FNO_KEEP=, the classic driver runs a preliminary Vtran/Intproc/Vcc/Fno pass to choose which virtual orbitals to freeze. Doing that in-process would call Vtran/Vcc twice, so the runner does this instead:

  1. Run Runscf.
  2. Temporarily change IFLAGS 2, 93, 83 and 100, and move NUMDROPA to FNOFREEZ.
  3. Call Acesjafin(), then run the standalone ../aces2/bin/{xvtran,xintprc,xvcc,xfno} as subprocesses (logs: fno_prelim_<exe>.log).
  4. Restore the flags; regenerate IIII with xvmol/xvmol2ja if it was consumed.
  5. Call Acesjainit(), then Runcc.

8.6 pyaces_run_case.py output protocol

python3 -u pyaces_run_case.py <workdir> <entrypoint> <iuhf> <record>
# progress: PYACES_CASE: ...
# success:  PYACES_CASE_VALUE: <repr>   /   PYACES_CASE_RESULT: SUCCESS <%.10f>
# failure (exit 1): IMPORT_FAILED, <ENTRY>_FAILED, RECORD_ZERO_OR_MISSING, DGETRECPY_FAILED

A record value of exactly 0.0 is treated as missing.

9.1 Running it

9.4 classify_suite.py is the source of the TSV

classify_suite.py builds the TSV from aces2/tests/fast/test_results and the ZMATs. Every routing rule lives in classify(), including the ones that were once hand edits: SCF_TYPE=KS → KS/Runintgrt, FOCK=AO MBPT(2) → Rundirmp2, and the exclusions for CCSD(TQ), BRUECKNER and HFSTABILITY=FOLLOW. PROGRAM=PCCD is excluded too: aces2/aces2/main.F hands such a job to xrunpccd, which runs xjoda again and the OO-pCCD loop, and Runpccd does not. Never edit the TSV by hand: change classify() and regenerate.

python3 classify_suite.py           # rewrite suite_classification.tsv
python3 classify_suite.py --check   # exit 1 and show the rows if the TSV differs from the rules
Roll-up: run_tests.sh reads every STATUS: n line of the runner's Summary block. PASS counts as PASS, MISMATCH and FAIL_CLEAN as FAIL, and everything else (CRASH, NO_RESULT, TIMEOUT, …) as OTHER, so TOTAL is always the number of cases run.

10. Extending pyaces: new entry points and new tests

10.1 Exposing a new Fortran routine to Python

  1. Make the aces2 side callable. If the target is a PROGRAM, split its body into a subroutine (the "wrapper-split" pattern used for dirmp2_run, intgrt_run, joda_, hbar_, props_). Rebuild aces2 first.
  2. Write a2_pyf/<name>.F.
    • Fixed form, with every #include starting in column 1 (oneAPI 2023.2 ifort rejects indented includes).
    • Declare every dummy argument explicitly as Integer*8 or Double Precision. A plain Integer makes f2py pass a 4-byte C int while -i8 Fortran reads 8 bytes.
    • Mark outputs with Cf2py intent(out) <arg>; the source is the only place signatures are defined (7.1).
    • The capitalisation of the subroutine name becomes the Python name.
    • Use Icore(i0), Icrsiz from icore.com/istart.com for core memory (see runcc.F). Do not call aces_fin.
    • Call aces2 routines by their real symbol: if aces2 defines SUBROUTINE HBAR_, the call must be Call Hbar_; Call Hbar would bind to a COMMON block (chapter 11).
  3. Add a lower-case wrapper to python/pyaces/drivers.py (and to runner.ENTRY_POINTS if it is a calculation entry point).
  4. Add the file to PYF_SOURCES in build.sh. The a2_pyf/*.F glob compiles it automatically unless it is on the exclusion list.
  5. Handle collisions.
    • If a newly pulled-in module has a PROGRAM, add it to MAIN_COLLISION_MODULES.
    • For a same-named routine, add rename <loser> <sym_> (and extract <loser> if needed) to tools/localize.txt.
    • If a pyaces object calls a renamed routine directly, add an objcopy --redefine-sym after step 3 (as done for runee.o).
    • If you re-enable a .skip module, add it to NEWLY_LINKED_MODULES.
  6. Build and check: "IMPORT OK", the new wrapper in the second (source-case) module build in f2py_gen.log, and print(aces2py.<Name>.__doc__).
  7. Handle NEW audit entries as described in section 6.3.
  8. Check that every name you call is code: nm Main/build/<name>.o lists the undefined symbols your object calls, and nm Main/build/aces2py*.so | grep ' <sym>$' must show T. B or D means the call is bound to a COMMON block.
  9. Add a test case and run the whole suite.

10.2 Adding a test case

  1. Add the case to the aces2 suite: aces2/tests/fast/cases/<name>/ZMAT and a three-line entry in aces2/tests/fast/test_results (name src / RECORD 1 / reference value).
  2. Run python3 classify_suite.py to regenerate pyaces/suite_classification.tsv, and check the new row (category, entrypoint, iuhf, record, ref_value). If the case is routed wrongly, change classify(), not the TSV. The entry's first line may be name src or just name.
  3. Check it with PYACES_SUITE_RUN_DIR=... python3 pyaces_suite_runner.py <name>, then read <dir>/run.log and summary.tsv.
  4. Make sure the full suites (./run_tests.sh aces2 pyaces) still pass.

11. Known issues (with fix history)

Fixed on 2026-10-23 (commit f97a9759): three defects found while writing this manual.
  • Call Hbar in Runhbar/Buildhbar: the symbol hbar_ is not a subroutine but lambda's COMMON /HBAR/ (B hbar_ in the .so), so the SCF-done and CC-done branches could jump into BSS. Changed to Call Hbar_ (= hbar__). The audit cannot catch this case because there is no T hbar_ anywhere, which is why step 8 of section 10.1 asks for an nm check. Verified with Init → Runscf → Runhbar on case 026 (CCSD energy matches the reference to 7×10-11).
  • Width of Iuhf: the Integer Iuhf in run*.F made f2py pass a 4-byte C int while -i8 Fortran read 8 bytes. Now declared Integer*8 Iuhf, so both sides are 64-bit.
  • Getreclenpy, Cgetrecpy: their outputs never reached Python. Cf2py intent(out) now makes them return the length and the string (section 7.4); the debug prints in Cgetrecpy were removed.
Fixed on 2026-10-23 (TODO stage 1: T-03, T-04, T-07, T-16)
  • Calls bound to data: collision_audit.py --calls now fails the build when a pyaces object calls a name the .so defines as data (section 6.1). It reports both hbar_ calls when run against the pre-f97a9759 objects.
  • Rename pairs that cannot apply: the build stops instead of ignoring them (section 5.2), and objcopy errors are no longer discarded.
  • Python version: the extension suffix comes from EXT_SUFFIX instead of a hard-coded cpython-312.
  • Test roll-up and classifier: the roll-up counts every status, the former hand edits are rules in classify() with a --check mode, and the runner's default run directory is inside the repository (sections 9.1–9.4).

The remaining issues below are present in the current code. They do not affect the paths the suite exercises today, but you will meet them when using or extending the affected features.
